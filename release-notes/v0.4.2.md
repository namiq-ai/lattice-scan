# lattice-scan 0.4.2

**A host scan now knows what the machine is and what is inside its container images.** Before, an image such as `postgres:16-alpine` was only a name, so a CISA-listed flaw in the Alpine packages inside it could never become a candidate, and the machine's maker, model and firmware were not recorded. What is matched against Lattice, how versions are compared and what leaves the machine are as in 0.4.1: only CVE ids (and a key, if you set one) are sent.

## Highlights

- **Hardware.** The inventory records manufacturer, model, version, board, firmware version and date, architecture, CPU, memory and whether the machine is virtual. Serial numbers and UUIDs are never read. A CISA entry for firmware or a board can match the machine's maker and model.
- **Inside container images.** For each image the tool reads the base OS and release and the package list (Alpine apk, Debian and Ubuntu dpkg, distroless images, and RPM images with sqlite databases), the version label and the `*_VERSION` variables. A CISA entry for `musl`, `busybox` or the image's own product (for example Redis 7.4.9 in `redis:7-alpine`) becomes a candidate that names the image and compares that image's package version. It also shows which local image each image was built on.
- **Two levels.** **Quick** (default) opens the images containers are running: about 12 seconds on the test host (7 running images). **Deep** (`--deep` or `LATTICE_SCAN_LEVEL=deep`) also opens every other local image and lists the Python, Node, Java and Ruby packages inside every image: about 6 minutes for 24 images (31 GB). After a quick scan one line on stderr says what was not read, how long deep takes and when it was last done.
- **Progress.** A deep scan prints a rough time estimate first, then `[n/N %]` with elapsed time per image, and a summary. `-q` prints none of it.
- **Short `--refresh`.** It prints totals, the hardware and an image summary (about 30 lines instead of about 2,800); the full lists stay in `inventory.json`, and `--list` prints them.
- **Safe to stop and to fail.** Nothing is started or pulled: images are read with `docker create` (stopped, no network, labelled), `docker cp` of two files, `docker rm`. The container is removed after each image, at exit and on Ctrl-C or SIGTERM, and the next run removes what a killed run left. One image that fails is skipped and named. Images are not opened when less than 1 GB is free where Docker keeps its data, and no new image is started after 30 minutes. Image environment values are never kept, except `*_VERSION`.
- The skill runs quick first, says what quick did not cover, offers deep only after the hint or a thorough request, and runs it in the background with one-line check-ins.

## What changes for you

- A host scan with Docker now makes a handful of `docker` calls per running image (about 12 seconds in total on the test host) before it asks Lattice anything. Set `LATTICE_SCAN_IMAGES=off` to skip them.
- A quick result is not "all clear": stopped images and the packages inside images are read only by `--deep`.
- A candidate found inside an image compares that image's package version, not the host's. The Debian changelog check applies to host packages only.

## Known limits

- RPM databases in Berkeley DB or ndb format are not read (sqlite only). Go and Rust binaries, Composer and NuGet inside images are not read.
- The deep time estimate is calibrated on one host.
- A run killed with SIGKILL can leave one stopped container until the next run (it is removed when older than 15 minutes).
- The tool still does not detect incidents or decide whether a host is affected. A match is a candidate for a person to read.
- The package is not listed in OpenAI's directory; submitting it is a separate step.
